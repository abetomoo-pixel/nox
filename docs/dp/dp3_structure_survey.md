### S1-4. ★予想人件費（money 隣接・慎重域として別記）

**現在の位置づけ**: モックの KPI 4枚目「予想人件費（時給ベース）¥65,000」は
**既に実装済み（a）**＝裁定19 段S-2。DP3 で**新規に触る必要はありません**。

**なぜ慎重域か（実装の実測）**:

- 計算の正本は **`lib/nox/labor-forecast.ts` の `forecastDay()`**（純関数）。
  **golden 55233**（`verify:nox-labor-forecast` 26 assertions）で係留されています。
- 時給の解決は**参照実装を書かず `pay.ts` の既存 export を再利用**（シフト1本を `sales=0/pts=0` の
  `DailyRecord` として `wageDetail` に渡す）＝**payOf とのドリフトが構造的に起きない**設計。
  丸めも payOf 規約（cast ごと `roundYen` の整数和）。
- 表示側は `fcByDate`（日→予想）を**1回だけ計算して KPI・カレンダー・日詳細で使い回す**
  （`shift-board.tsx:369-384`）。月次ロールアップ（E8-4 #4）も**その合算のみで新規計算なし**。

**DP3 での扱い（提案）**: **不触**。理由＝
①**モック構造としては既に満たされている**（KPI 4枚目・月次サマリとも実装済み）
②golden 55233 と payOf 再利用の設計に触れる利得が無い
③触るなら「時給ベース」の但し書きの文言くらいで、それは DP2 相当の意匠。
→ **もし DP3 で表示を動かす指示が出る場合は、`forecastDay()` の入出力に一切触れないこと**を
条件にしてください（`verify:nox-labor-forecast` が検出器として働きます）。

## シフト深部レーンへの申し送り（DP3 で d と確定した分）

1. **`wish_id` 保持要件（原型対比の前提）** — モックの `adjustDialog` は「**元の希望**」と調整後を
   並べて見せる。NOX は `shifts` に希望の原型を持たず、`wishes` は採用時に紐が残らないため出せない。
   → **`shifts.wish_id`（nullable・`wishes` 参照）を持たせるのが最小の前提**。
   採用経路（`shift_wish_decide` の accept）で書き、手動追加では null。
   これが入って初めて「希望 20:00–26:00 → 確定 21:00–26:00」の対比が描ける。
2. **4段フロー＝`status` 拡張とセット** — 表示だけ先に入れることは **DP3-④ で禁じた**（教訓25）。
   4段（希望→管理者確認→キャスト確認→確定）を出すなら、`shifts.status` を
   現行2値（`planned`/`confirmed`）から**中間状態を持つ語彙へ拡張**し、
   各段の遷移 RPC と「誰が進めたか」を同時に設計する（E8 `shift#6`＝T6）。
   **表示と状態は同じコミットで入れる**こと。
3. **貪欲法の移植は可**（**DP3-④**） — 裁定2「AI シフト最適化＝実装しない」の射程は**学習型のみ**で、
   **規則ベース（貪欲法などの決定的アルゴリズム）は対象外**と明確化された。
   E8 `shift#7` が止まっている理由は裁定2 ではなく**配置ルールを保持する列/テーブルが無いこと**。
   → 先に**配置ルールのスキーマ**（何を優先するか・上限/下限・NG 組合せ 等）を設計する。
   出た配置は**たたき台**であって確定ではない（モックも「自動配置（たたき台）」と書いている）＝
   人が修正できる導線（`undoAuto` 相当）を同時に持つこと。
4. **その他の d** — 下書き/公開ライフサイクル（`shifts` に status も公開日時も無い＝T6）／
   計画ビュー（#3 に従属）／`adjustNote`（`shifts` にメモ列が無い）。
