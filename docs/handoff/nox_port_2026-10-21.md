### (e) NOX に移すときの注意（BANZEN 側の事実）

- 設定の単位は「店」（`stores` の行）。テナントの下に店が複数ある前提。
- role 名 `hq / manager / staff / parttime / kiosk` を RPC と route が直に比べている。manager は「自店」＝`auth_store_id()` の 1 店だけ。
- 「店の端末のみ（tablet）」は kiosk role の端末を指す。本人のスマホからの打刻はハードで断る（裁定551）。キオスクの打刻は別の RPC（0046 など）。
- ハードでも完全には止めない。範囲外は理由を書けば通る（0165）。止まるのは tablet の店と、予定外の block だけ。
- 判定は TS 側。DB の CHECK・RPC は値の形しか見ない。
- IP は Vercel の `x-forwarded-for` 先頭を信じる作り。ホスティングが変わると読む場所が変わる。
- 範囲が未登録なら、ハードでも通す（`evaluable=false`）。
- 丸めは「表示と計算だけ」。DB の打刻は変えない。法令の同意を DB でも強制している。
- 営業日の区切り `stores.business_day_start`（0190）を予定外の判定が使う。

### (e) NOX に移すときの注意（BANZEN 側の事実）

- LINE の設定・チャネル・LIFF・Webhook はすべて「店」単位（storeId）。テナント単位ではない。
- 1 staff＝1 LINE（テナント内）。紐付けは招待トークン（bind）が信頼の境目。
- LINE でのログインは Supabase のマジックリンクをサーバーで作ってセッションにする作り。スタッフの auth ユーザーのメールが要る（合成アドレス `@staff.banzen.jp` を使う）。
- 上限は「表示のための設定」。アプリは送るのを止めない。月の境目は JST の暦月（LINE の区切りも JST とみなしている＝push-forecast.ts:2）。
- 台帳の kind は 2 種類だけ（DB の CHECK）。通知を足すと CHECK と `PUSH_KINDS` の両方を変える必要がある。
- 見込み客デモでは送らない（`isDemoTenant`）。BANZEN だけの仕組み。
- 再ログインの cookie 名 `bz_line_store`・ドメイン `banzen.work` は BANZEN 固有。
- role：上限の設定と集計は manager（自店）と hq。staff・parttime は見ない。
