## x5 うまくいかなかった点（正直に）

1. **check_pay の p_tendered**＝cash 以外（card／ar）は null 必須（'bad tendered'）＝script の誤り（PoC 1 回目）。録画の作り手が RPC の引数規約を守る必要があるだけで 276-1 の障害ではない。
2. **stock_logs の sale 行の日付**＝再生時に check_lines INSERT のトリガが `at = now()` で作る＝在庫台帳の日付は「今日」になる（伝票は 3 日前）。by_user_id も null（service には auth.uid() が無い）。対策候補＝(a) 投入後に tx 内で `update stock_logs set at = <伝票の営業日相当>` を product×check_lines.created_at の対応で当てる（stock_logs に check_id は無い＝行の対応は product_id＋順序）／(b) 在庫台帳は「今日基準で減った」でよしとする（デモの在庫画面は最新残だけ）／(c) 0149 で stock_on_check_line に「INSERT 時の at を new.created_at に寄せる」補正（mig＝トリガ変更・在庫 suite の pin に影響）。
3. **audit_logs の再生**＝target が採取 id の 30 行を payload に入れて再投入できた（at も相対化）。ただし actor（actor_user_id）は録画時の owner＝demo では固定 users なので成立。set_store_* の audit（店設定変更）は target 外＝再生しない。
4. **時間帯料金**＝A1 は pricing_rules 0＝check_open は store の set_fee／ext_fee で解いた（帯なし）。「録画時に set_store_time_pricing を同一 tx 内でずらして狙った帯で解かせる」案＝**通った**（x0 で set 5,000／延長 3,000 に変えて開いた伝票がその値で凍結）。帯（pricing_rules）を持つ店では check_open が `pricing_resolve_core(now())` で**録画時刻の帯**を引く＝夜の帯を録るには録画を夜に回すか、tx 内で該当帯の rule を一時的に「全時間帯」へ広げて解かせる（set_pricing_rule の同 tx 更新→ROLLBACK）＝次の実証点。
5. **延長**＝started_at を過去へ UPDATE してから check_time_charge_apply＝95 分で set 1＋延長 2 が乗った（276-1 の想定どおり）。manual 店でも apply は動く（time_mode の判定なし）。
6. **now() 既定の列**＝select * で全列を持つため上書きなし（created_at／paid_at／closed_at も相対化して戻した）。identity／generated 列＝0。
7. **daily_report_close は正規経路で通った**が、open 伝票が残っていると 'open checks remain'（1 回目で踏んだ＝5 枚全てを close する前提）。
8. **削除の再入**＝check_lines の DELETE で stock_logs sale_remove が再生成（2 行）＝u1 と同じ。demo_org_reset では stock_logs を check_lines の後にもう一度 delete（w2 53 手目）。
9. drink_claims・receipt_issues・approvals・print_jobs・check_seats・reservations は今回の 5 枚に無く **0 行＝再生の実証は未**（drink_claims の approved 行を含む再生は次の実証点）。
10. audit を含めると payload が約 2 倍（30／63 行・字数の半分超）＝org 3 MB 級。RPC の引数（jsonb）としては可だが Vercel→PostgREST の 1 リクエストで 3 MB を送る前提の確認が要る。
