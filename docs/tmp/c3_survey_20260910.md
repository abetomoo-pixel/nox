観察:
- 「解除」の実装は **payroll_reopen のみ**（D-1・service 経路・owner authz は route）。日報は解除の器が無く reclose＝再集計上書き。伝票は void のみ（訂正版の再確定なし）。回収は取消なし。
- 理由必須は **check_void だけ**。reopen 系は理由列なし（audit_logs.reason は 0135 で追加済み・audit_log_write に p_reason あり＝器は揃っている）。
- 既存 audit action（live 実数）: check_void 42／daily_report_close 4／daily_report_reclose 1／payroll_finalize 27／payroll_reopen 3／set_staff_perms 14／staff_change_role 2／staff_deactivate 3。横断 §3 の 10 種のうち **report_reopen／cash_diff_approve／check_merge／price_snap_fix／perm_change は未使用**（perm_change 相当は現行 'set_staff_perms'・report_reclose 相当は 'daily_report_reclose'）＝action 名の揃え方が裁定要。
- 締め済み日の伝票操作ブロックは **どの check_* RPC にも無い**（prosrc に daily_reports 参照 0）＝解除型の「解除→訂正→再締め」を作るなら、締め済み日の伝票書込を止める関所（daily_reports 行あり→raise）を同時に置くか裁定要（D24）。

## 2. 権限 4 層（横断 §2）の live

- memberships の can_* 列＝**can_register／can_crm／can_shift／can_view_backs の 4 列のみ**。`can_close`／`can_reopen` は**未存在**（参照する関数も 0）。
- set_staff_perms(p_membership_id, p_can_register, p_can_crm, p_can_shift, p_can_view_backs)＝5 引数・audit action 'set_staff_perms'。横断 §2 どおり **6 引数化（can_close／can_reopen 追加・旧署名 DROP・A6 名簿更新）**が 0138 の同梱対象（#63）。
- can_* の使われ方: can_register＝レジ系 RPC 多数＋auth_staff_can_register（RLS にも）／can_crm＝顧客・予約 RPC＋auth_staff_can_crm／can_shift・can_view_backs＝ヘルパーと set_staff_perms のみ（RPC 判定では未使用）。
- 解除型 RPC の判定句（横断 §2）: `auth_role() in ('owner','manager') or (auth_role()='staff' and can_reopen)`＝ヘルパー `auth_staff_can_reopen()`／`auth_staff_can_close()` を auth_staff_can_* 同型（SECURITY DEFINER・STABLE・authenticated 可）で新設するのが既存流儀。
- flag `reopen_flow` を参照する関数は flag_set（whitelist）のみ＝ゲート呼出は 0。C② と同型＝各解除型 RPC 冒頭で `flag_enabled('reopen_flow', store)` false→`raise 'feature_disabled:reopen_flow'`（C②-10 の書式）。

## 3. check_merge（伝票 2 枚→1 枚）の器

- merge／combine 系関数＝**無し**。checks に **`merged_into uuid references checks(id)` が休眠列として存在**（0006 で列のみ・0053 で「案A 採用により未使用・drop しない」）。live 値＝81 伝票中 merged 0。
- 関係表の凍結列・制約（逐語は live dump §3）:
  - checks: status check（open／closed／void）・凍結列＝service_rate／round_unit／round_mode／set_*／ext_*／vip_charge_*／time_per／price_display／tax_rounding／category_id・close_idem_key・closed_at・nom_type（hon／jonai／dohan／free）・people・customer_id。unique なし（seat 占有は check_seats）。
  - check_lines: kind check・fee_kind check（set／extension／dohan／hon_shimei／jonai_shimei／ext_shimei／vip_charge）・pay_group（A〜F 等 1〜20 字）・name_snapshot／unit_price_snapshot／line_total／back_snapshot／tax_category（凍結）。check_id FK のみ（unique なし）＝行の移送は `update check_lines set check_id` で可能だが pay_group の衝突（両伝票に同じ A）は意味論の裁定要。
  - check_nominations: **UNIQUE (check_id, cast_id)**・ratio_weight／nom_kind／is_dohan／position＝同一 cast が両伝票にいると統合で衝突→weight の合算か一方採用かの裁定要。
  - check_seats: check_id FK **ON DELETE CASCADE**・seat_id＝統合先へ付け替え可。
  - payments: check_id FK・idem_key・pay_group・method（cash／card／ar／other）＝**入金済み伝票の統合は金額整合（ar→receivables.check_id）を壊す**＝「payments が無い open 伝票同士のみ統合可」が最小安全域。
  - receivables.check_id（FK）・drink_claims.check_id（FK・check_line_id ON DELETE SET NULL）・check_cast_backs **UNIQUE (check_id, cast_id)**（close 時に生成＝open 統合なら未生成）。
- 統合の最小形（裁定材料）: 元伝票 B を A へ＝check_lines／check_nominations（重複 cast は weight 合算）／check_seats／drink_claims の check_id を A へ・B は status='void'（void_reason='merged'）＋`merged_into=A`・B の open receivables／payments が無いことを前提条件（あれば 'not mergeable'）・合計は A で再計算（check_group_due 経路）・audit 'check_merge'（before＝B の要点・after＝A の行数）・理由任意（横断 §3 #5）。

## 4. D45 入金方法別照合（B2 裁定206 で据え置き）

- B2 調査表 D45: receivable_collect は cash／card／other を受理（0092 検証）・UI は "cash" 固定・理論在高加算は cash のみ（daily_report_aggregate の `p.method='cash'`）。
- payments.method check＝cash／card／ar／other（実分布 cash 42／card 14／ar 4）・method_detail（50 字）あり。ar_collections.method check＝cash／card／other（実分布＝0 行）。
- daily_reports の列＝cash／card_gross／card_tax／uri／other／ar_collected（**cash 回収のみ**・列名に方法なし）。aggregate は payments を method 別に合算済み（cash／card／ar／other）＝**入金方法別の売上照合は既存列で足りる**。足りないのは **売掛回収の方法別**（ar_collected が cash 限定・card／other 回収は日報のどこにも載らない）。
- 既存読取で足りるか: 回収の方法別は `ar_collections(method, amount, biz_date)` の client 集計 1 本で出せる（B2-b の D47 と同じ表）。日報の凍結列へ載せるなら **daily_reports に ar_collected_card／ar_collected_other を足す mig**（aggregate 改修＝money 境界＝Fable）。UI の p_method 可変化（select）は RPC 変更なしで開通するが、現金照合式（cash のみ加算）との整合＝「カード回収は現金在高に入れない」を画面で明示する必要。
