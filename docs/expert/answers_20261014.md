1. 日払いの5,000円控除・雇用キャストの日額表
委託キャストのホステス報酬について、国税庁の2026年4月1日現在の取扱いは、
源泉税 =（報酬額 − 5,000円 × 計算期間の日数）× 10.21%
です。

「計算期間の日数」は出勤日数でも、日払いした回数でもなく、その支払金額を計算する基礎となった期間の初日から末日までの暦日数です。

なのでNOXでは、日払い回数 × 5,000円 という実装にはしない方がいいです。
日払いを2種類に分けるのが一番安全です。
日払いの実態	NOXでの扱い	5,000円×日数
その日の報酬をその日に確定して支払う	日次精算	1日分＝5,000円
半月・月次報酬の一部を先に渡す	前払・仮払	日払いのたびに自動控除しない
1〜15日分をまとめて確定	半月精算	15日分＝75,000円
月全体をまとめて確定	月次精算	28〜31日分


例えば、9月4日の報酬20,000円をその日の報酬として完結して支払うなら、
(20,000 - 5,000) × 10.21% = 1,531円
です。

一方、
1〜15日を給与・報酬期間としていて、途中で9/3・9/7・9/10に1万円ずつ日払い

のようなものが「仮払い」なら、3回だから5,000円×3回とする設計にはしない。過去のホステス源泉事件でも、勤務当日の「日払い」が最終精算とは別の仮払いとして扱われていた事例があります。
したがってデータとしては、
daily_payment_type = settlement / advance
を持たせたいです。

さらに重要なのが雇用キャストです。雇用ならホステス報酬の10.21%式ではなく給与所得として処理します。国税庁は、毎日払い・週払い・日割払い等には日額表、月払い・半月払い・10日ごとの支払いには月額表を使うとしています。扶養控除等申告書ありなら原則甲欄、なしなら乙欄です。

そして「日払いだから丙欄」ではありません。丙欄は日雇賃金の要件を満たす場合だけです。2か月以内の有期雇用などが典型で、2か月を超えれば丙欄は使えません。国税庁
つまりNOXは、

契約区分
→ 雇用 / 委託
支払・精算方式
→ 月次 / 半月 / 週次 / 日次精算
途中払い
→ なし / 前払・仮払
を別フィールドにするべきです。
「日払いON」という1個のフラグから源泉方式を決めるのはやめたいです。

2. 「報酬調整（契約）」の労働者性注記
台帳291追補1で進めていた考え方は維持してよいです。厚労省も、契約名が業務委託かどうかではなく、指揮監督、拘束性、仕事を断る自由、代替性、報酬の労務対償性など、実際の働き方から総合判断するとしています。
画面文言はこれにしたいです。
業務委託として登録しても、法令上の労働者性や税務上の所得区分が確定するものではありません。
仕事を断る自由、業務上の指揮監督、勤務時間・場所の拘束、代替性、報酬の決め方など、実際の働き方によっては労働者に該当する場合があります。

さらに「報酬調整（契約）」画面なので、その下に短く、
報酬の減額・控除を設定する場合は、契約上の根拠と実際の運用が一致していることを確認してください。

を追加。
これなら「NOXで委託を選択すれば委託になる」と誤認させません。厚労省自身も、フリーランスであっても実態によって労働者となり得ると明示しています。厚生労働省
これは今までのNOX方針とも一致しています。


3. 店舗向け利用規約は雛形先行してよいか
開発・社内テスト・デモ段階なら、雛形先行で問題ないです。
L7のデモ規約とは別に、店舗向けを v0.9 として先に実装して構いません。
ただし、実店舗が本番データを入れる時点はゲートのままにしたいです。
特にNOXは、顧客情報、キャスト情報、売上、給与・報酬関連データまで扱います。個人データを外部SaaSへ委託する場合、委託元には委託先の安全管理を適切に監督する義務があり、その合意は必ずしも独立した契約書でなくても、約款等で客観的に明確化できればよいと個人情報保護委員会も説明しています。個人情報保護委員会
なのでローンチ前の店舗向け規約には最低でも、
サービス内容 / アカウント管理 / 利用料金・支払 / 店舗データの取扱い / 個人情報 / 再委託 / 禁止事項 / バックアップ・データ保持 / 解約時のデータ / メンテナンス・停止 / 知的財産 / 免責・損害賠償 / 契約解除 / 規約変更 / 反社 / 準拠法・管轄
までは入れたいです。
NOX側では同意履歴として、
terms_version
accepted_at
accepted_by_user_id
organization_id
を保存。
店長がチェックボックスを押しただけで全店舗ユーザー個人が契約者になる設計ではなく、店舗・法人単位の契約同意として記録する方がきれいです。
結論としては、
デモ規約：L7のまま完了
店舗向け利用規約：雛形v0.9で先行実装OK
本番店舗開通：店舗向け規約への同意を必須ゲート
で進めるのがいいです。
この3点なら、特に源泉部分は仕様書にそのまま入れておいた方がいいです。今の max(0, round((報酬−5,000×日数)×0.1021)) だけだと、**その「日数が何か」と「日払いが精算か前払か」**が抜けていて、そこが一番事故りやすいです。
